# Receipt participants: preview, picker, rows, roles and debt actions

Owners: separate functional and visual specs in `packages/app/features/receipt-components/__tests__/` for `receipt-participants`, `receipt-participant`, `receipt-participant-role-input`, plus `packages/app/features/receipt/__tests__/receipt-participant-actions.*`. Extend the receipt fixture with named picker, participant-row, role and action locators. Supply coherent owner and guest data, generated balances, matched/missing/desynced debts, and local vs foreign peers. Default receipt fixtures have no connected users, no receipt-level payers, and every participant consuming every item, so override generators for missing states.

## Preview and picker own these scenarios

- With zero participants, the “Add participants” preview opens the picker. With participants, preview shows payer avatars (or a dimmed owner fallback when no payers), shows “for” avatars only for **nonzero consumer debt totals**, and opens on either the preview or pencil. Test one/multiple payers, zero/nonzero debt and guest foreign-avatar behavior; do not confuse debt total with balance.
- Owner picker lists rows owner-first and then by creation time, filters already-added peers, and offers self as an extra suggestion only if not already present. Selecting a peer sends `receiptParticipants.add({ receiptId, peerId, role: "editor" })`; pending selection cannot be repeated, success updates the picker/preview, and failed addition releases temporary selection. `receiptDisabled` disables the suggestion. Guest picker has no suggestion and, if empty, displays its empty card. Opening/closing without mutation must work.
- Clip empty/populated previews, loading preview skeleton and owner/guest picker in light/dark. In screen-level shots mask the separately tested accordion rows while preserving the picker layout and suggestion.

## Individual participant row owns these scenarios

- A collapsed row displays peer, formatted debt total, optional money icon and payment line, and dims a non-consuming non-payer. Expanding exposes the payer control, item breakdown, role and injected action. Show payer totals only when relevant; show consumer subtotals for multiple consumed items, append `+` for shortage, and ignore a debt item absent from the receipt rather than crashing.
- “+ payer” adds a receipt-level payer with `receiptItemConsumers.add({ itemId: receipt.id, peerId, part: 1 })` (this endpoint is intentional, not an item-level payer call). Editing a positive part uses the corresponding `receiptItemConsumers.update` with type `part`; zero removes using `receiptItemConsumers.remove`. Assert total-parts denominator, autosave on input blur, immediate zero/add transitions, invalid values not mutating, pending/success/error and rollback. Scope the textbox by its accessible payer-part label.
- Owner removes a zero-balance participant immediately; nonzero balance requires confirmation, with cancel preserving the row and confirm calling `receiptParticipants.remove({ receiptId, peerId })`. Cover optimistic consumer cleanup, failure rollback and pending. Guest sees no removal button. Do not infer that backend authorization permits removing the owner's own row merely because UI draws that control.
- Owner viewing another nonzero-balance peer: absent debt warns “no ours”; mismatched amount is danger; connected peer with matching ours but missing or mismatched reverse debt gets the appropriate warning; matching sides and unconnected peers show no reverse warning. Zero-balance and own row have no warning. Guest sees no warnings for other participants but should get own missing/mismatched incoming debt warnings, comparing debt amount to **negative** participant balance. `debts.get` in this row is a non-suspense optional query; no outcoming ID should skip it, not create a fabricated query error. Capture collapsed/expanded, dimmed, validation, removal and distinct warning/tooltip states in clipped visuals.

## Role control and per-peer action each own separate tests

- “Pick role” displays Owner/Editor/Viewer but offers only Editor and Viewer. The owner can change another participant's role with `receiptParticipants.update({ receiptId, peerId, update: { type: "role", role } })`; unchanged selection is a no-op; failure restores prior role. Disable it for guest, owner-row, disabled receipt, or matching pending mutation, without disabling unrelated peer rows. Clip normal, open and disabled visuals.
- Per-peer actions appear only for an owner looking at a different participant. Zero balance yields a zero icon; nonzero without outgoing debt yields “Send debt to a peer” calling `debts.add` with balance, peer, receipt date/currency/ID and receipt note; existing mismatched outgoing debt yields “Update debt for a peer” calling `debts.update` with the new amount/currency/timestamp/receipt ID. A matching own debt shows `DebtSyncStatus`, even if only the reverse side differs; test its in-sync and warning directions separately. Assert pause/loading, failure/rollback, suspense fallback and query error at the action boundary. The row's own debt warning and header's bulk `ReceiptSyncButton` have different owners: do not duplicate either screenshot here. Mock responses with the cache controllers' expected IDs/timestamps.

Important behavior to document rather than assume away: the participant row does not guard its payer-part controls for guest users. If a new authorization rule is desired, it needs a product change before a test expecting disabled guest controls.
