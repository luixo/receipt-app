# Add-receipt builder and draft state

Owner: extend `packages/app/features/add-receipt/__tests__/add-receipt-screen.spec.ts`, `.visual.spec.ts` and `utils.ts`. Existing tests already cover empty form/date/top currency, invalid short receipt name, empty-draft submit failure/loading/success/redirect and basic empty/form screenshots. The missing `add-receipt/hooks.ts` paths represent **local draft editing**, not network mutations. Use the real `/receipts/add` page; reuse separately tested receipt child controls from [participants.md](participants.md), [item-collection.md](item-collection.md), and [item-controls.md](item-controls.md).

## Functional expectations

- Open “Item”, save two valid local items with distinct names/prices/quantities, then edit the first name, price and quantity by blurring the inline fields. An unconsumed item appears in “Items with no participants”; after success the form remains open and resets for another. Removing an unconsumed item is immediate; removing one with consumers asks for confirmation and supports cancel. The final `receipts.add` input contains only surviving items with latest fields, **without temporary IDs/timestamps**. No `receiptItems.add/update/remove` API calls happen during draft edits.
- Open participant picker; add self from its special suggestion and two distinct suggested peers, each once. New selected participants have role `editor` (including explicitly added self); change a peer to `viewer`, remove a zero-balance peer, and add it again without duplicates. Assert picker and preview reflect state and the final payload includes only surviving `{ peerId, role }` entries. A default dimmed owner preview does not mean a payer was added. Seed suggestions and mock peer lookups.
- Expand selected participant rows; “+ payer” changes preview to real payer avatars. Add a second payer, update a numeric part, inspect the total-parts denominator, and lower one part to zero so its payer record is removed rather than sent with zero. Final receipt `payers` carry the updated peer/part pairs only. Local draft payer actions should **not** call `receiptItemConsumers` before final submission.
- In an item select a first consumer, making its warning disappear; select a second, change its part from one to two, check ratio and participant calculated amounts, then remove a consumer by setting zero or deselecting. “Consumed by everyone” with two or more missing adds only missing peers at part one without replacing an existing edited part. Final item `consumers` have correct pairs exactly once and no timestamps.
- Test an item-specific payer override: owner is the dimmed default, choosing a non-owner changes display and calculated payment, and clearing the override restores fallback. **Current product gap:** `AddReceipt` discards `item.payers` when constructing `receipts.add` input even though the backend accepts them. Do not write a falsely passing persistence expectation; record that test as dependent on a separately authorized fix. `updateItemPayerPart` is not reachable through the current selector UI.
- In **one integrated payload test**, combine surviving edited items, two participant roles, receipt-level payer parts, unequal consumer shares, changed issued date/currency and name. Assert `receipts.add` receives complete arrays with no UI-only IDs/timestamps/sums and does not implicitly insert self as a payer/participant. Mock `receipts.get` for the destination **before** resolving add and assert navigation to the returned ID. This is distinct from the existing empty-draft submit test.
- Invalid item fields block item Save but must not disable an otherwise-valid _receipt_ submission. Invalid inline item or part inputs must leave the last valid draft values intact. Without a top currency the draft may display `???`, but final add must remain invalid until currency is selected. A populated draft whose `receipts.add` throws `TRPCError` remains on the page with all draft state for retry and an asserted/consumed error toast.

## Visual expectations

Capture in light/dark an item-creation card with the unassigned-item warning, a participant picker with expanded role/payer-part state, and a populated item with payer/consumer selectors and two part rows. Prefer named clipped locators from `utils.ts`; take one full-page composition shot if it meaningfully tests how preview, warning and cards fit together. In a **screen-owned** screenshot mask the independently tested child controls/rows but leave the parent layout and draft-state placement visible. In clipped child-owned snapshots leave the child unmasked. Settle peer requests/autosaves and consume toasts first.

## Do not manufacture frontend paths

`hooks.ts` guards against stale item/participant/payer IDs, duplicate peers, absent arrays and thrown React state setters. Normal UI cannot reliably reach most of those branches; do not inject contexts or mutate React state from DOM evaluation solely to reach a line. Removing an active draft participant currently does **not** clean up that peer's item consumers or payer records despite the confirmation wording; ordinary zero-balance removal is testable, and the active-consumer cascade needs a product decision/fix rather than a passing test for behavior not implemented.
