## Functional scenarios by test owner

**`receipt-name-input.spec.ts`:** On an owner receipt, click the header pencil and check it replaces the heading with “Receipt name” and its Save control. Saving the original name closes edit mode without `receipts.update`; a dirty invalid short name blocks Save and shows validation feedback. Saving a different valid name sends precisely `{ id, update: { type: "name", name } }`; pause to check loading/disabled Save and optimistic heading/cache as applicable, then resolve and check the new heading. Make an update throw `TRPCError`: check toast and cache rollback, that editing is still available, and that retry succeeds. Avoid asserting a document-title update after a mutation without rerunning the route loader: the route title is initialized from loader data.

**`receipt-date-input.spec.ts`:** Read the original issued date in the test browser timezone. Recommitting the same day must not mutate; choosing a different `Temporal.PlainDate` calls `receipts.update` with type `issued` and updates the display. Pause and reject a changed-date mutation to check disabled/loading, optimistic cache then rollback/toast, followed by a successful retry. A guest sees a disabled date field. Do not pause `receipts.get` to test the date control.

**`receipt-amount-input.spec.ts`:** Supply multiple items whose `price * quantity` yields a nontrivial rounded sum; assert the displayed number and currency symbol are computed from them, not an editable amount. Owner can open the picker; selecting the current code closes it without mutation, while another code calls `receipts.update` with type `currencyCode` and refreshes the symbol. Pending must prevent reopening; failure restores the prior code and displays/consumes the error toast, then a retry succeeds. Guest cannot open the picker. Check the currency symbol's real accessibility/DOM contract before choosing a locator.

**`receipt-remove-button.spec.ts`:** Nonempty owned receipt: menu → Remove opens confirmation, cancel does not mutate, confirm calls `receipts.remove({ id })`. While a paused removal is pending, shell editing, date, currency, item-add and participant-add controls that depend on `receiptDisabled` should be unavailable; the optimistic receipt may disappear before some pending elements can be observed, so assert only visible states supported by the actual UI. Success invalidates the receipt list and navigates with replacement to `/receipts`; mock `receipts.getPaged` for the destination. Failure leaves/reinstates the receipt, restores usable controls and reports an error. With zero items removal skips confirmation. Consume mutation/success/error toasts according to the real descriptor rather than assuming the generic RemoveButton emits none.

**`receipt-guest-control-button.spec.ts`:** For a coherent incoming guest receipt with `debts.id` and `hasMine: true`, the titled icon link goes to `/debts/$id` (and carries the debt ID as hash); with `hasMine: false` it goes to `/debts/intentions`; with no ID it does not render. Assert destination URLs after clicking with their required mocks. The outgoing-debt guest guard represents invalid fixture data, not a normal UI scenario to fabricate.

**`receipt-screen.spec.ts`:** Assert owner/guest shell structure and permissions at the page boundary: heading, back link to `/receipts`, owner avatar, amount/date, correct owner sync vs guest debt control, and absence of owner edit/delete affordances for guest. Keep this an integration assertion rather than repeating all child mutations above. A `TRPCError` from `receipts.get` should show the route-level error rather than a resolved shell. The screen fallback structurally includes heading/date/avatar, amount and participant placeholders and **three** item skeletons; attempt a client transition only if it really displays that fallback. The route loader prefetches the query, so **never pause the initial SSR `receipts.get`** simply to force loading—it may hang the stream. If fallback cannot be reached reliably, document the limitation rather than creating a flaky spec.
