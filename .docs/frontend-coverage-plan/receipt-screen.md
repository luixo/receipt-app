# Receipt detail screen: metadata, ownership and navigation

Owners: new `packages/app/features/receipt/__tests__/receipt-screen.spec.ts` and `receipt-screen.visual.spec.ts`; extend `utils.ts` with stable locators. The existing `receipt-sync-button.*` tests own the sync control; participants and item controls belong to their own slices. Baseline `receipt-screen.tsx` has 16/18 statements but important guest/edit branches untested; name input and guest debt control are barely exercised.

## Functional expectations

- An owned receipt shows its heading, date, total in the selected currency, owner avatar, edit/removal affordances and sync button. Back goes to `/receipts`; mock `receipts.getPaged` before following the link. Verify its route ID and that the displayed total comes from rounded item price × quantity, not an editable amount.
- Opening the name pencil replaces the heading with “Receipt name” and Save. Unchanged name closes without `receipts.update`; an invalid short name prevents saving. Saving a changed valid name sends `{ id, update: { type: "name", name } }`, presents pending feedback, updates the heading on success, and remains editable after a `TRPCError` so it can be retried. Check optimistic cache and rollback with query snapshots; consume expected toasts.
- Changing the date (rather than blurring unchanged date) sends `receipts.update` of type `issued`; choosing a different currency (rather than the existing one) sends type `currencyCode` and updates the symbol. Check pending disabled/feedback and failure/retry. Reuse the existing currency picker fixture rather than duplicating its internal interactions here.
- For a nonempty receipt, removal asks for confirmation; cancel does nothing, confirm sends `receipts.remove({ id })`, disables screen controls during a paused request and replaces the route with `/receipts` on success. An empty receipt removes directly without confirmation. A failed removal keeps the receipt visible, restores the controls and reports an error. Mock the destination list query before success.
- A guest fixture must have a _different_ owner peer, a real self participant and `debts.direction: "incoming"`; merely switching `ownerPeerId` while retaining outcoming debts is invalid. There is no name pencil, removal menu or bulk sync control. The date/currency and owner-only add operations are unavailable. With an incoming debt ID and `hasMine: true`, the guest debt control links to `/debts/$id`; with `hasMine: false`, to `/debts/intentions`; without an ID, no control appears. Verify destination queries when following the links. The outcoming-debt guest guard is an invariant, not a normal UI journey.
- A failed `receipts.get` should show the route error, not a half-rendered receipt. The structural loading layout has heading, date/avatar, amount/participant placeholders and three item skeletons. Do **not** pause the initially SSR-prefetched `receipts.get`; only prescribe a loading test if a client navigation or streaming setup actually exposes it without hanging.

## Visual expectations

Capture owner and guest shell in light/dark with deterministic names/peers/date/currency, including a narrow viewport if layout changes. Mask the participant preview/modal, item cards and separately snapshotted sync control; retain header, metadata placement, total, avatar and owner/guest affordances. Clip a header-edit state and a nonempty removal confirmation as separate shots; capture error/fallback only if reachable through the real route. Named fixture locators, settled peer queries and toast cleanup are required. A clipped rounded card/dialog may need `mapExpectedPixels` to sample an interior pixel.
