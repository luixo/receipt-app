# Receipt item card and independently implemented controls

Owners: paired functional/visual specs for `receipt-item`, `receipt-item-name-input`, `receipt-item-price-input`, `receipt-item-quantity-input`, `receipt-item-consumer-input`, `receipt-item-payers`, `receipt-item-consumers` under `packages/app/features/receipt-components/__tests__/`. Reuse receipt fixtures with one deterministic item and named card/field/menu/row locators. Keep `ownerPeerId`, `selfPeerId`, participant roles and incoming/outgoing debt direction coherent. `useCanEdit` allows owner/editor, not viewer; guest editor uses foreign-peer queries. Do not model guest by removing self from participants (missing self falls back to owner role).

## Each child owns its own behavior and clipped light/dark visuals

- **Item name:** owner/editor gets an inline “Receipt item name” field and viewer sees plain text. Unchanged blur and invalid short/long names do not mutate; valid changed blur sends `receiptItems.update` of type `name`. Match pending state by item ID and update type; show spinner, success, and failed optimistic rollback/toast. Snapshot resting, dirty validation, pending and viewer variants tightly around the field.
- **Price:** owner/editor gets “Receipt item price” with currency symbol, two-decimal validation and an update of type `price` on changed blur; viewer gets formatted text. Check unchanged/zero/precision/max cases, item total recalculation, pending isolation from name/quantity updates and failure rollback. Snapshot editable/symbol, invalid, pending and viewer values.
- **Quantity:** owner/editor gets “Receipt item quantity” with `p/u` postfix, viewer gets `x … unit`. Check positive fractional value, zero/precision/max validation, changed-blur `receiptItems.update` of type `quantity`, recalculated total, pending/error and no-op unchanged. Snapshot postfix, invalid, pending and viewer. For both number controls, locate by role `textbox` and label, then blur after filling; assert actual behavior rather than a contradictory max-error string.
- **Per-consumer part:** for more than one consumer, owner/editor sees a ratio button with part controls and an editor that autofocuses when opened; viewer sees a static ratio. The denominator is the rounded sum of _all_ consumer parts. Positive changes autosave (delayed unless blurred), zero removes via `receiptItemConsumers.remove({ itemId, peerId })`, nonzero sends `receiptItemConsumers.update` with type `part`; invalid part, unchanged value or disabled item must not mutate. Assert pending/check/error, optimistic rollback and peer/item-specific isolation. Clip the control, not the peer row; generic plus/minus visuals already have tests in `part-buttons`.
- **Item payers:** `Select` “Choose a payer” falls back to dimmed owner when `item.payers` is empty; explicit payer selection adds with `receiptItemPayers.add({ itemId, peerId, part: 1 })`, removal uses `receiptItemPayers.remove`. Verify one-selected peer versus group rendering, owner/foreign peer lookups, option ordering, pending consumer mutation disabling possible non-owner options and error rollback. The select is single-select in current UI; do not demand a multiple-payer interaction. Viewer does not see it because the parent omits the selector row. Clip default, explicit, open and disabled-option states.
- **Item consumers:** `Select` “Choose consumers” is multiselect, displays up to three avatars and joined peer names; owner queries `peers.get` and guest editor `peers.getForeign`. Add/remove distinct IDs via `receiptItemConsumers.add/remove`, each with exact item/peer and part one for add. Pending disables only affected peer options, not all peers; failure restores selection. Test none/one/many, names loaded later and foreign identity. Clip selected, open and pending states. Parent handles orphaned consumers.

## Card composition owns these behaviors

- Card shows name, price × quantity and rounded currency total; payer-selector → arrow → consumer-selector row stacks on mobile and runs horizontally at `sm`. One consumer gives no per-consumer rows; two or more show chronologically sorted rows and per-peer parts. With at least two consumers, a consumer missing from receipt participants displays an orphan error mentioning the peer ID instead of a peer row. Do not force inconsistent fixture data that crashes upstream calculations.
- “Consumed by everyone” appears only with **more than one** participant missing from item consumers and adds each missing peer once at part one, without replacing existing shares. It is **not currently guarded by edit permissions**: test behavior as observed, flag authorization separately, and do not invent a viewer-disabled guarantee.
- Owner/editor sees ellipsis → “Remove item”. With no consumers it removes directly; with consumers it confirms, permits cancel, then sends `receiptItems.remove({ id: item.id })` and updates cache. Check failure rollback, pending where observable, and item control disabling while removal stays mounted. Viewer sees plain value controls, no menu or payer/consumer selector row.
- Parent **card** visuals at narrow/desktop widths own composition, totals, arrow, “everyone”, orphan message, dropdown/confirmation, skeleton and conditional rows; mask the six child-owned field/select/control regions and separately snapshotted peer/avatar content, leaving their positions visible. Child screenshots clip only to the child and do not snapshot the whole card. Identify cards with a named unique item locator; `ReceiptItem` currently has no own `testID`.

Mock mutations before navigation, use `api.createPause()` for pending, `TRPCError` for failures, cache snapshots for optimistic/rollback claims, and consume error toasts before visuals. Add success responses with `createdAt` where the cache controller requires it.
